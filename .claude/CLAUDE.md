## 役割と作業の進め方

- 開発作業は agy（要件整理・調査・`handoff.md` 作成）、Claude Code（実装・テスト）、Codex（レビュー）で分担する。
- 作業ディレクトリのルートに `handoff.md` がある場合は、実装前に必ず内容を確認し、要件・受け入れ条件・スコープ外・実装方針に沿って作業する。
- `handoff.md` の内容と実際のコードに食い違いや不明点がある場合は、自己判断で仕様を変えず、実装前にユーザーへ確認する。
- スコープ外の変更や不要なリファクタリングを行わない。
- 実装後は `handoff.md` に記載された検証方法（テスト・lint 等）を実行し、結果を報告する。
- Codex のレビュー指摘をもとに修正する場合は、指摘の妥当性を確認したうえで必要な修正と再検証を行う。
- `handoff.md` は引き継ぎ用の一時ファイルなので、`git add` / `git commit` の対象に含めない。

## AWS / GitHub の認証情報が必要な作業

- どのラッパーで起動したかは、システムプロンプトに追記される。追記が無いときは、通常のセッションとして扱う。
- 通常のセッション（`claude-safe`）では、AWS の資格情報（`AWS_*`）や GitHub の資格情報（`GH_TOKEN`）が必要な作業を行わない。
- 認証情報が必要になったら作業を止め、次の起動方法をユーザーに案内する。
  - AWS: `claude-aws <profile> -- <args>`
  - GitHub: `claude-gh -- <args>`
- `claude-aws` か `claude-gh` で起動したセッションでは、そのラッパーに対応する認証情報を使う作業を行ってよい。
  もう一方の認証情報が必要なときだけ、起動し直しを案内する。
- `claude-gh` のセッションでも、`git push` や非公開リポジトリの `git fetch` のように GitHub の認証が要る git の操作は行わない。必要になったら、実行するコマンドをユーザーに伝えて実行を頼む。
- `claude-gh` のセッションでは `gh` で GitHub の API を使う操作を行ってよい。PR や Issue の作成、コメントの投稿のように GitHub に書き込む操作は、実行前に承認を得る。
- セッションの中から、起動方法自体を切り替えることはできない。案内後はユーザーが起動し直す。
- 認証情報の値を、ファイルに書いたり、コマンドに直接埋め込んだりしない。
- `~/.aws`、`~/.config/gh`、`.env` などの認証情報ファイルを読もうとしない。

## 変更の承認

- ファイルを変更する前に、変更内容の diff を提示し、承認を得てから変更する。
- `git add` と `git commit` の前に、必ず承認を得る。承認の前に、`git diff` で内容を確認できるようにしておく。
